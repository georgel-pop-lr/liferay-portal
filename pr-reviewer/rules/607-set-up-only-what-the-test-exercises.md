# 607: Set Up Only What the Test Exercises

Keep a test strictly to the method it is named after (rule 603) and to the branch its scenario drives. Every mock, stub, spy, `MockedStatic`, and fixture it adds must sit on the path its assertions reach, and every assertion must be about the result of that method. Before keeping a setup step, trace the code under test from the asserted call: if deleting the step would not change which branch runs or what the assertion sees, delete it. A stub that only restates the mock's default (`thenReturn(false)` on a `boolean` getter, `thenReturn(null)` on an object getter) is deleted too.

This covers setup copied from a neighboring test because it is the class's usual shape (a stub for a getter this scenario never calls, a pushed `ServiceContextThreadLocal`, an extra group or user, a `MockedStatic` opened for a utility this case never reaches), and assertions about behavior the test is not named after, which belong in that other method's test.

Do not overdo it. Setup shared through `@Before` or a factory helper that other tests or scenarios in the class use is not a violation for the one test that skips it, and a stub a scenario helper needs is not a violation because its sibling helper does not. Judge only what the pull adds or modifies, never setup it did not touch.

**Rationale:** Setup reads as a claim that the code under test depends on it, so an unneeded stub misleads the reader about what the behavior requires and has to be carried through every refactor of the subject. It can also hide the bug: pushing a `ServiceContext` in `LayoutServiceContextHelperTest` steered the test onto the branch with a context, while the production caller (reindex) runs the null-context branch. Nothing else catches it: none of the 740 test files under `modules/apps` that use Mockito enable strict stubs (no `Strictness.STRICT_STUBS`, no `MockitoJUnitRunner.StrictStubs`, counted at `24e6a0c4eb7e9`), so an unused stub passes silently. Generated tests, a model's included, tend to over stub, which is why every added test is worth this check.

The shared-setup exemption is calibrated on a real run. `LayoutsAdminDisplayContextTest` on LPD-105565 was run once under `Mockito.mockitoSession().strictness(Strictness.WARN)`: Mockito reported 15 unused stubs across its 5 tests, and every one was `@Before` or factory-helper setup that another test or scenario in the class does use. The stubs the pull added were all reached. Flagging Mockito's list as it stands would have produced 15 false findings.

A violation is a mock, stub, spy, `MockedStatic`, or fixture that an added or modified test creates for itself and that its assertions' path never reaches, a stub returning the mock's default value, or an assertion in that test about a method other than the one it is named after.

**Example:** commit `f49e78615b5a6` (`LPD-99344 Drop redundant false stubs on Mockito boolean mocks`) deleted `Mockito.when(layout.isPrivateLayout()).thenReturn(false)` stubs from `LayoutActionsHelperTest`, 12 lines that restated the mock's default. Commit `b038bf3d80653` (`LRCI-7783 Remove the unused mocks and stubs`) removed a `Mockito.spy` and a `.git` directory fixture from `PortalWorkspaceGitRepositoryTest` and `WorkspaceGitRepositoryTest` that no assertion depended on.
