# 206: Keep Homogeneous Peer Statements Together

A run of sibling statements that perform the same operation on the same receiver is one paragraph, and so is a run of adjacent declarations of the same type that form a preamble with no use between them. Do not separate either with blank lines. Three consecutive `_fragmentsImporter.importFragmentEntries(...)` calls, or `fragmentCollection1` and `fragmentCollection2` declared back to back, read as one unit and should be laid out as one.

The source formatter wins wherever the two disagree, and it errors rather than repairs, so a blank line deleted under this rule can fail the build rather than be quietly restored. `MissingEmptyLineCheck` requires a blank line before a statement when the statement above it holds the last reference to a variable, which is far narrower than that paraphrase reads. `_checkMissingEmptyLineAfterVariableReference` at `modules/util/source-formatter/src/main/java/com/liferay/source/formatter/checkstyle/check/MissingEmptyLineCheck.java:150-196` walks forward from the declaration and gives up at the first following statement that does not name the variable, unless the chain has already begun. So a declaration whose very next sibling ignores it is never revisited however far down the real last use sits, while a chain that runs unbroken is enforced at the exact line where it ends. Read the check before deciding, because the paraphrase on its own points both ways and has produced findings in both directions that the formatter then refused. Apply this rule only to a run that is genuinely uniform: the same receiver, the same operation, and no reference chain ending inside it.

Setters on one receiver count as one operation even when they set different things. `setAttribute` followed by `setParameter` on the same request is one configuration block, not two paragraphs. Across the Java files under `modules/apps`, Commerce excluded, 31,170 adjacent pairs of different `set*` calls on one receiver sit solid against 7,811 separated by a blank line, and some of those 7,811 are blank lines `MissingEmptyLineCheck` requires.

Assertions on one predicate count as one operation too. An `Assert.assertFalse` and an `Assert.assertTrue` whose predicates call the same method check that method with two inputs, so they are one block even though the assertion methods differ, and a blank line between them splits one thought. Counted over the test sources in `modules/apps` outside Commerce on 2026-09-26, adjacent `assertTrue`/`assertFalse` pairs whose predicate calls the same method sit solid 440 times against 43 separated by a blank line. Once the pair is solid it is a run, and rule 202 sorts it on the predicate's arguments. Brian Chan closed up exactly this pair in `DesignLibraryUtilTest.testIsConnectedDesignLibraryGroupId` on LPD-105566 Use the design library group when adding a page from its page template set (https://liferay.atlassian.net/browse/LPD-105566), https://github.com/brianchandotcom/liferay-portal/pull/182430#issuecomment-5836850839. Assertions about different subjects, such as a check on a caught exception followed by a check that no layout was created, are two thoughts and keep their blank line.

**Rationale:** A blank line is a paragraph break, and a reader takes it as a claim that what follows is a new thought. Spending one between two calls that differ only in their arguments spends the strongest layout signal available on nothing, and it hides the real breaks in the method by putting a break everywhere. Keeping a uniform run solid makes the one blank line that does separate two ideas mean something again.

Rule 203 sets each declaration off from the statement that uses it, which is the opposite case: there a blank line separates two different thoughts, while here it would split one.

A violation is blank lines between consecutive calls of the same operation on the same receiver, consecutive setters on one receiver and `assertTrue`/`assertFalse` calls on one predicate method included, or between adjacent declarations of the same type that form one preamble, where no variable's last reference falls between them. This rule only ever deletes a blank line. A missing one belongs to `MissingEmptyLineCheck`, not here, and since the check fails the build rather than inserting the line it is worth reporting, but only once you have read the check and confirmed the chain reaches that statement unbroken.

**Counter-example:** on LPD-104425 the rule was read off the shape alone against `FragmentEntryLinkDisplayContextTest.testGetSearchContainer`, where a blank line splits `layoutFragmentEntryLink1` from the four `FragmentEntryLink` declarations below it. The reasoning was that `group` is used further down, so no last reference falls there. Closing the block up fails the build with "There should be an empty line before line 141, as we finished referencing variable group": the next declaration calls `GroupTestUtil.addGroup()` rather than `group`, which ends the chain at that line, and the check never looks past the break to the later uses. The sibling `FragmentEntryLinkLocalServiceTest` runs its own `FragmentEntryLink` declarations solid for the same reason, because its helpers take no `group`. Both files follow the formatter; only the eyeball reading of them differed.

**Example:** on LPD-106071 Administer display page templates from the Design Library (https://liferay.atlassian.net/browse/LPD-106071), Brian Chan's SF commit `f7a89a622f73c` (https://github.com/brianchandotcom/liferay-portal/commit/f7a89a622f73c8a3a0595de408ed7a162bc7e9f0) deleted the blank line between `mockLiferayPortletRenderRequest.setAttribute(...)` and `mockLiferayPortletRenderRequest.setParameter(...)` in `EditDisplayPageMVCRenderCommandTest`.
