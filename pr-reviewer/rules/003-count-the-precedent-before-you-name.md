# 003: Count the Precedent Before You Name

Before introducing a name the codebase does not already carry, count it: `git grep --cached <fragment>` against the kind of file you are editing. Zero or one hit is a finding on its own, not merely the absence of one, because a concept the codebase already names was renamed rather than reused. Several hits means a convention exists, so match it and fix the outliers already in the tree in the same pull.

Run the probe the way it actually finds things:

- Grep a fragment of the name, not the whole name. Dropping the first character defeats camelCase position, so `ommonField` finds `commonField` and `getCommonFields` in one pass, and `LibraryHref` finds every name that ends in it.
- Scope it to the kind of file you are reading rather than to the repository: `**ServiceImpl.java`, `**Constants.java`, `**ResourceTest.java`, `**service.xml`.
- Pass `--cached`, and add `-3` or `-B2` when the point is to compare the form of the neighbors rather than to count them.

A count of zero is not a violation by itself, because a new class earns a new name and so do the names derived from it. What separates the two cases is the word pair census: split the name into its camelCase words and count each adjacent pair. A name whose leading pair is well established and whose trailing pair is 0 has a new word grafted onto a concept the codebase already names, and that is the violation. A name where no pair of it exists either is new vocabulary, which is a question for the author rather than a verdict.

Singularize the last word before you call a trailing pair 0. The probe matches characters, so a plural never matches its own singular, and the plural is always the rarer spelling: counted over `modules/apps` on 2026-09-22, `Counts` sits in 54 files against 5,112 for `Count`, `Entries` in 2,405 against 11,431 for `Entry`, `Names` in 5,351 against 21,813 for `Name`, and `Ids` in 4,016 against 25,148 for `Id`. A trailing pair that reaches 0 only in the plural therefore says nothing about the concept, which the singular already names, and the plural is what the return type asks for when the method hands back a collection. Count the singular too, and treat the pair as established when the singular is.

Count the leading verb of a method name as well, against the siblings that do the same job. The census is built to catch a new trailing word, so a name whose nouns are all established passes it even when its verb is the invention: `_newCreationItem` ends in `CreationItem`, the tail of its own return type `DesignLibraryResourceCreationItem`, while `_new` leads 7 private helpers in `modules/apps` outside Commerce against 2,597 named `_get` plus their exact return type. A verb that its siblings use a handful of times against thousands for another is the same violation, and rule 109 supplies the replacement.

Rule 001 says to follow the existing name when one is already used widely, and rule 002 says to pick one form when the file carries two. This rule is the step before both: you cannot follow a convention you never looked for, and the count is what turns a hunch about a name into a citable finding. Cite this rule for the absence itself, and beside it the naming rule that supplies the replacement, which on the example below is rule 107: the count is what makes the name a violation, and the naming rule is what says which name to use instead.

**Rationale:** The probe costs one grep and the defect it catches is expensive. A renamed concept costs every later reader a synonym to learn and every later grep a second spelling to remember, and it is invisible in review because the diff reads consistently with itself. Only a count against the rest of the tree shows it. Measured on 2026-09-22 over the comments on `brianchandotcom/liferay-portal` since 2026-06-18, 52 of Brian Chan's 5,500 review comments are this grep and its result, and they draw two verdicts and only two: the name was invented, or a convention exists and the outliers go with it.

A violation is a name the diff introduces that master uses zero times where the concept it names already has an established name, shown by the count on an existing sibling or on the name's own leading words. A name that master already uses a handful of times, which the diff then spells a second way, is the same violation from the other side, and fixing it covers the outliers already in the tree. A new class, and the names derived from it, are not violations. Neither is a plural whose singular the codebase already carries.

**Example:** LPD-105565 List the connected design library page template sets in the add page selector (https://liferay.atlassian.net/browse/LPD-105565) was closed over one name out of the 72 the branch added: "git grep designLibraryHref / only returns 1 result" (https://github.com/brianchandotcom/liferay-portal/pull/182189#issuecomment-5767456609). `designLibrary` runs to four figures in master while `LibraryHref` is 0, a new word on an established stem, and the replacement, `selectLayoutPageTemplateEntryURL`, had precedent. The same verdict elsewhere: "Only one result. That's a big warning sign. You had to invent a new naming scheme" (https://github.com/brianchandotcom/liferay-portal/pull/177874#issuecomment-4840382567) and "shows nothing prior to this PR.. so it still seems like we're introducing a new naming/concept when unnecessary" (https://github.com/brianchandotcom/liferay-portal/pull/180316#issuecomment-5314699290). The other direction, where the count is not zero: `g grep --cached "extends BaseExportImportTestCase" **.java` gave "It shows other violations as well ... Please fix existing violations as well" (https://github.com/brianchandotcom/liferay-portal/pull/181057#issuecomment-5477943571), and `g grep --cached -5 updateExternalReferenceCode **ServiceImpl.java` gave "hey, most are the OTHER way ... Please make them all consistent" (https://github.com/brianchandotcom/liferay-portal/pull/180927#issuecomment-5451917772).

The census misreads a plural without that normalization. On LPD-101584 it read `getGroupFragmentEntryUsageCounts`, a service method returning `Map<Long, Integer>`, as a violation, because `sageCounts` is in 1 file of master while `etGroup` is in 8,139, `ragmentEntry` in 724, and `ntryUsage` in 50. `sageCount` is in 73, so the trailing word is established and only its plural is new, and the one master file that does carry `sageCounts`, `_mailMessageCounts` in `MailEngine.java`, is a `Map` of counts keyed by an id, the same shape. The name was correct and the finding was withdrawn.
