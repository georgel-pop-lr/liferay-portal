# 605: Override Every Generated Resource Test Method

In a `*ResourceTest` that extends a `Base*ResourceTestCase` (generated by REST Builder), override every test method the generated base defines and annotate the override with `@Override @Test`. The override delegates to `super.testX()` first to preserve the generated coverage, then calls any private `_testX*` helpers that add scenarios for the same REST path. A new `*ResourceTest` test scenario goes inside the matching override as a `_testX*` helper — never as a new top-level `@Test` method.

**Rationale:** The generated `Base*ResourceTestCase` defines one test method per REST path, so the set of overrides in the subclass tells a reader at a glance which paths the suite exercises and that none was silently skipped. The naming chain — `_testGetSiteFragmentApprovedAndDraft` called from `testGetSiteFragment` — keeps every scenario attached to its path, so adding a new case never disconnects from the path it tests. A new top-level `@Test` method in the subclass severs that link: the reader cannot tell which path it covers, and the corresponding `super.testX()` may end up unreachable.

A violation is a `*ResourceTest` extending a `Base*ResourceTestCase` that does any of:

- adds a top-level `@Test`-annotated method whose name does not match a base test method (the scenario should be a `_testX*` helper called from the corresponding `testX` override);
- omits `@Override` on a method that does match a base test method;
- declares a `_testX*` helper whose `X` prefix does not match the parent override's method name in the same class;
- overrides `testX` without calling `super.testX()` first, dropping the generated coverage. The one exemption is a `test<Verb><Parent><Entity>PermissionsPage` override whose `<Parent>` is neither `Site` nor `AssetLibrary`, such as `testGetDesignLibraryPageTemplateSetPermissionsPage` or `testPutDesignLibraryDisplayPageTemplatePermissionsPage`: it is not a violation, whether the scenario sits inline or in `_testX*` helpers. Recognize it from the method name alone. The generated base is an `@generated` file, so it is never in the diff, and the reviewed checkout may not contain its current version. REST Builder fills a permissions test's parent path parameter only for the site (`testGroup`) and the asset library (`testDepotEntryGroup`) and passes `null` for every other parent (`portal-tools-rest-builder/.../base_resource_test_case.ftl:4522`), so `super.testX()` would request `/<parent>/null/...` and fail. The exemption covers the `*PermissionsPage` methods only: a sibling override such as `testGetDesignLibraryPageTemplateSet` has a `testX_get<Parent>ExternalReferenceCode()` hook the subclass overrides, so it still calls `super.testX()` first.

Counted on 2026-09-29 in `modules/apps`, all 4 `*PermissionsPage` overrides whose base passes `null` skip `super`, 4 to 0: `testGetDesignLibraryDisplayPageTemplatePermissionsPage` and `testPutDesignLibraryDisplayPageTemplatePermissionsPage` from LPD-106070 Complete the display page template API at Design Library scope (https://liferay.atlassian.net/browse/LPD-106070), and the page template set pair from LPD-107400 Add the design library page template set permissions REST paths and action (https://liferay.atlassian.net/browse/LPD-107400).

Two more overrides are exempt for the same reason, again recognized from the method name alone, because the generated base cannot reach the path it is named after. A `testPatch<Parent><Entity>` override: REST Builder passes `null` for every parent path parameter that is neither the asset library id nor a property of the DTO (`base_resource_test_case.ftl:1545`), so `BaseMasterPageResourceTestCase.testPatchSiteMasterPage` calls `patchSiteMasterPage(null, ...)` and `super` would request `/<parent>/null/...`. A `testPost<Parent><Entity><Action>` override for an action path such as `Copy`, `CopyWithPermission`, `MarkAsDefault` or `UnmarkAsDefault`: the generated body only adds an entity through the `testX_add<Entity>` hook and asserts it equals the random one, so it never calls the action, and for a copy, whose name and external reference code are new, its assertion cannot hold. Counted on 2026-10-05 in `modules/apps`, 16 of the 17 parent-scoped `testPatch` overrides skip `super`, and the design library action overrides in `DisplayPageTemplateResourceTest` skip it 4 to 0, as `MasterPageResourceTest` from LPD-81022 Design Library Scope for Master Pages (https://liferay.atlassian.net/browse/LPD-81022) does. `testPost<Parent><Entity>` and `testPut<Parent><Entity>` are not exempt: their hooks are the subclass's to override, so they still call `super.testX()` first.

**Example:** PR `175757` (`AssetEntryResourceTest`) added scenario logic outside the override-plus-`_testX*`-helper structure. The fix is to add an `@Override @Test public void testX() { super.testX(); _testXFoo(); _testXBar(); }` and move the new scenarios into private `_testXFoo` / `_testXBar` helpers whose `X` prefix matches the overridden method.
