# 202: Sort Sortable Sequences Alphabetically

When a sequence of sibling items has no order imposed by dependencies or logic, sort it alphabetically. This applies to consecutive method calls on the same object, the parameters of a method, sibling declarations such as fields, methods, and functions, and lists of string or key literals. The Liferay source formatter sorts variable, field, and method names in case sensitive natural order: `JavaTermComparator` in `modules/util/source-formatter` builds `new NaturalOrderStringComparator(true, true)`, whose second argument is case sensitivity, and that comparator returns the uppercase side first when exactly one of the two characters at which the names diverge is uppercase. So `_criterionType` is declared before `_criterions` in `CriterionImpl`, and `testGetActionDropdownItemsWithUsageCount` before `testGetActionDropdownItemsWithoutManageFragmentEntries`, because `T` and `U` beat `s` and `o`. Counted over `modules/apps` on 2026-09-23, sibling declarations that differ by case at the character where their names diverge run uppercase first 2,563 times against 12 the other way, so never resort a declaration on a case insensitive reading of the name. Literal strings sort case sensitively in ASCII order, with spaces and digits before letters, uppercase letters before lowercase, and `null` last.

Several constraints override the default sort. Setter calls on a generated model mirror the defining schema rather than sort alphabetically: a ServiceBuilder entity follows the column order in its `service.xml`, and a REST DTO follows the field order in its `rest-openapi.yaml`. In a constructor body, assignments from constructor parameters come first and follow the parameter order, with any derived assignments after them (see `JavaConstructorParametersCheck` in the same source formatter directory). A vararg parameter is forced to the end of a parameter list by the Java language. A group of functions or methods first orders public before private, then sorts alphabetically within each group; see rule 907. Java fields sort the same way: `JavaTermComparator` ranks every class member by access modifier, `static`, and kind before it ever compares names, and a `private static` field outranks a `private` instance field, so `_layoutPageTemplateCollectionLocalServiceUtilMockedStatic` is declared before `_layoutPageTemplateCollection` even though the instance field's name is a prefix of the static one. Counted over the hand-written classes in `modules/apps` on 2026-09-23 that hold both kinds of private field, 4,819 declare every static field first and none interleave them, so compare names only between two fields that share the same modifiers.

When the items are repeated calls or constructions of one shape, the sort key is the whole rendered item, compared argument by argument from left to right: the first argument groups the items, the second orders them inside each group, and so on. Sorting on the first argument alone and leaving the rest arbitrary is a violation, because a reader who has found the group still cannot predict where an item sits inside it. Counted over the `List.of` and `Arrays.asList` literals in `modules/apps` that hold three or more entries of one constructed type, 25 sort on every argument and 2 sort on the first alone.

When the sequence is a run of sibling statements rather than repeated calls on one object, the sort key is still the whole rendered statement compared left to right, so the receiver sorts first and the method name only breaks ties inside one receiver. `AdminPortletDataHandler` in `knowledge-base-web` runs `_kbArticleLocalService.deleteGroupKBArticles`, `_kbFolderLocalService.deleteKBFolders`, then `_kbTemplateLocalService.deleteGroupKBTemplates`, which sorting on the method name would reorder, since `deleteGroupKBTemplates` precedes `deleteKBFolders`. Counted over the runs of three or more consecutive `_field.method(...)` statements in `modules/apps` that hold more than one receiver and more than one method name, 27 are sorted on one of the two keys: 20 where both keys give the same order, 5 sorted on the receiver and not on the method, and 2 the other way, of which one is Commerce and the other leaves its receivers unsorted. Brian Chan asked for this on LPD-104558, https://github.com/brianchandotcom/liferay-portal/pull/181663#issuecomment-5633820627, against a block of five `Assert.assertThrows` calls that ran in the order the operations would be performed rather than in any order a reader could derive. Sorting a run can move a local's last reference, and `MissingEmptyLineCheck` then demands a blank line where the reference chain ends; take the blank line, since the formatter wins.

A run of two or more consecutive unqualified calls sorts the same way, the setup helpers a test invokes on itself among them. There is no receiver to sort on, so the method name carries the key. Counted over `modules/apps` on 2026-09-23 across runs of consecutive single line unqualified call statements with distinct names, test sources run 2,791 sorted to 116 unsorted and production sources 4,366 to 266, and the `setUp` helpers in test sources alone run 198 to 16; the unsorted side is an upper bound, since a run whose order a dependency imposes belongs there. When such a run mixes a private `_setUp` helper with one inherited from a base class, the leading underscore is ignored: all 9 mixed runs in `modules/apps` sort on the name with the underscore stripped, against 4 of those 9 that also hold with it counted, so strip it. Brian Chan asked for this on LPD-101584, https://github.com/brianchandotcom/liferay-portal/pull/182175#issuecomment-5763930185, closing the pull over a `setUpFragmentPermission` / `_setUpFragmentEntry` pair with "sort? or if dependency matters, add a line break", which is also the order to follow when the two readings disagree.

When the consecutive calls share one method name, the name gives no order, so the arguments carry the key, compared left to right as for any repeated call of one shape, and `false` sorts before `true`. A reading of the calls as a scenario, the disabled case first and then the enabled one, is not a dependency and does not override the sort. Counted over `modules/apps` outside Commerce on 2026-09-24, adjacent statements that call the same unqualified method and differ in a leading `true` or `false` argument put `false` first 112 times against 35, and all but one of those pairs sit in test sources. Brian Chan applied this himself on LPD-101584 in commit `5bc00818e125` (https://github.com/brianchandotcom/liferay-portal/commit/5bc00818e1250bfed6511404cace3beab94552f2), moving `_assertViewSiteUsagesDropdownItemDisabled(false, RandomTestUtil.randomInt())` above `_assertViewSiteUsagesDropdownItemDisabled(true, 0)`.

A run of consecutive `Assert.assertEquals` calls is the exception to comparing left to right: it sorts on the actual value, the last argument, because that is the subject each line asserts on, while the expected value and the message in front of it only describe the outcome. Two consequences follow. The checks on one collection stay together and run in the order of their actual expressions, so `x.get(0)` and `x.get(1)` come before the `x.toString(), n, x.size()` check on the same collection, and the checks on `x1` come before those on `x2`. The expected values do not reorder anything, so `Assert.assertEquals(fragmentEntryLink2, fragmentEntryLinks.get(0))` stays above `Assert.assertEquals(fragmentEntryLink1, fragmentEntryLinks.get(1))`. This has no counted precedent and the corpus leans the other way: counted over `modules/apps` outside Commerce on 2026-09-25, a size check adjacent to a `get` check on the same collection comes first 153 times against 21, and of 1,703 runs of three or more `assertEquals` calls, 590 sort on the actual argument (209 of which also sort on the first), 519 sort on the first, and 803 on neither. It is what Brian Chan applied himself on LPD-104560 in commit `1d573a94d937c` (https://github.com/brianchandotcom/liferay-portal/commit/1d573a94d937c25936b806579166958560c1ff96), reordering four such runs in `FragmentEntryLinkLocalServiceTest`, so report it on assertions a pull adds or moves, and never on untouched ones.

A run of `Assert.assertTrue` and `Assert.assertFalse` calls whose predicate calls the same method is the second exception: it sorts on the predicate's arguments, compared left to right as for any repeated call of one shape, and the assertion method gives no order, because which of the two a line uses follows from its input rather than from where the line belongs. Counted over the test sources in `modules/apps` outside Commerce on 2026-09-26, of the 483 adjacent `assertTrue`/`assertFalse` pairs whose predicate calls the same method, 345 are sorted on the arguments against 138, while putting the `assertFalse` first fits 261 against 222, no better than chance, so never group the falses ahead of the trues to tidy a block. Brian Chan applied this on LPD-105566 Use the design library group when adding a page from its page template set (https://liferay.atlassian.net/browse/LPD-105566), https://github.com/brianchandotcom/liferay-portal/pull/182430#issuecomment-5836850839, moving `Assert.assertFalse(DesignLibraryUtil.isConnectedDesignLibraryGroupId(companyId, RandomTestUtil.randomLong(), groupId))` above `Assert.assertTrue(DesignLibraryUtil.isConnectedDesignLibraryGroupId(companyId, designLibraryGroupId, groupId))`, since the uppercase `R` of `RandomTestUtil` precedes the lowercase `d` of `designLibraryGroupId`. The two lines had sat in scenario order, the connected case first, with a blank line between them; rule 206 closes that blank line, and the pair is only a run to sort once it does.

When one sequence mixes two forms of the same kind of value, for example `Layout.class.getName()` beside the string literal `"com.liferay.style.book"`, group by form and sort inside each group instead of interleaving them: the constants first, then the string literals. The two forms share no comparable text, since `Layout.class.getName()` sorts nowhere near the fully qualified name it resolves to, so an interleaved sequence has no order a reader can derive. This one has no counted precedent, as the mixed shape does not occur in `modules/apps`; it is what Brian Chan asked for in review on LPD-104558, https://github.com/brianchandotcom/liferay-portal/pull/181514#issuecomment-5602955934.

**Rationale:** A sequence in arbitrary order forces the reader to scan all of it to find one item and scatters new items into random positions, which makes diffs noisier. One predictable order lets any item be found at a glance and gives every addition an obvious place. Sorting yields to a real constraint: when one item depends on, or must run before, another, that order wins over alphabetical order.

A violation is a sequence of sibling, order independent items left in an order that is not alphabetical — setter or getter calls on one object, a parameter list, sibling declarations, or the entries of a literal list.

**Example:** commit `a72be4fa` sorted a block of `themeDisplay.set*` calls and `172687f` ordered `setPortalDomain` before `setPortalURL`; `fb69012` reordered parameters to `(Account account, Long accountId)`; `19d4dbf` alphabetized shell functions; `d461c0b` fixed a string list to the case sensitive order `" 1 "`, `"0"`, `"0, 1"`, `"true"`, `null`; `f264e2c` sorted a test method into its alphabetical position among its siblings. Pull https://github.com/brianchandotcom/liferay-portal/pull/181526 was closed over `LayoutPageTemplateDepotRolePermissionsContributor`, whose twelve `DepotRolePermission` entries sorted on the role constant and then ran `RESOURCE_NAME`, `LayoutPageTemplateCollection`, `LayoutPageTemplateEntry`, `Layout` inside each role: "this seems random to me, I can't figure out the pattern".
