# 503: Extract a Single Use Local Only When It Earns Its Name

A local used exactly once earns its declaration only when its name states something the expression does not. Otherwise pass the expression inline at its one use site. A nested call that is passed inline as an argument stays inline, however deep it is and however many arguments the outer call takes. Ask for a local in place of a nested call only when a variable in the same scope already holds the value of that call, so that the code can pass the variable and not make the call again.

Ask for a local when either of these hold:

- A variable in the same scope already holds the value, and the code makes the same call again inline. Pass the variable. The repeated call must give the same value: `LayoutTestUtil.addTypePortletLayout(group)` adds a new layout each time, so a second call is not a repeat.
- The name captures a concept the raw expression does not state, such as `viewMode` for `ParamUtil.getString(PortalUtil.getOriginalServletRequest(request), "p_l_mode", Constants.VIEW)`.

The depth of a nested call and the argument count of the call it feeds do not ask for a local. On `brian/master` at `7e98727e96370`, outside Commerce, `modules/apps` passes a one level nested call inline as an argument of a call with three or more arguments 9182 times in production code and 16108 times in test code. Against that, 2019 and 1365 single use locals hold such a call and feed such a call. A one level nested call is a call whose own arguments are only names, literals, or no-argument getters. The shape of the LPD-108819 example below, a nested call as the first argument whose result goes to a local of the same type, occurs inline 12 times, and the extract and reassign form `layout = update(layout, ...)` occurs 0 times. A variable that already holds the value while the code makes the same call again inline, the case that this rule still reports, occurs about 48 times.

A no-argument getter does not count as a call level. `getGroupItemSelectorURL(getGroupType())` is one call deep, not two. The extraction `String groupType = getGroupType();` names the value after the getter and adds nothing, and it matches `(?i)_?get<VariableName>`, so `VariableDeclarationAsUsedCheck` can reject it. On `upstream/master` at `4450e5d83b5c4`, outside Commerce, `getX(getY())` with a no-argument inner getter occurs inline 790 times in `modules/apps`, 652 of them in production code.

A `String.valueOf(...)` wrapper does not count as a call level either. It converts the value to text and states nothing a name could add, so `breadcrumbEntry.setURL(String.valueOf(getGroupItemSelectorURL(StringPool.BLANK)))` is one call deep, and it stays inline. On `brian/master` at `318e9227de210`, outside Commerce, production code in `modules/apps` passes `String.valueOf(<call with arguments>)` inline as an argument 196 times, against 6 single use locals that hold it, and a setter receives it inline 9 times, against none through a local. LPD-109452 Technical Task | Browse sites and Design Libraries in the group selector (https://liferay.atlassian.net/browse/LPD-109452) kept the inline form.

The source formatter overrides both triggers. A trigger above is a reason to want the local, never a licence to ship one the build rejects, so where the extraction fails `formatSource` the argument stays inline and the trigger simply does not apply. Read the checks named in the first constraint below before asking for an extraction, since a precedent elsewhere in the same file settles nothing: they turn on the lines around the declaration, not on the expression being extracted.

Otherwise inline it. A single use local whose name only echoes the call that produced it adds a line to read and an indirection to resolve for nothing.

Three constraints bound the call:

- The source formatter polices one corner of this, so its silence is not approval and its refusal is final. `VariableDeclarationAsUsedCheck` rejects a single use local only when the initializer is a getter named after the variable, matching `(?i)_?get<VariableName>` in `BaseAsUsedCheck._matchesGetOrSetCall`, and only when the local is then passed as a parameter rather than used as a receiver. So `String canonicalURL = PortalUtil.getCanonicalURL(...)` used once is rejected with "No need to declare variable", while `String alternateURL = _generateURL(...)` used once passes. Two further conditions decide whether it fires at all. `BaseAsUsedCheck.checkInline` counts the blank lines between the end of the declaration and its single use and bails out above one, so the identical shape passes where an unrelated declaration sits between the two and fails where nothing does. And `ReturnVariableDeclarationAsUsedCheck`, which no other rule names, forces the returned variable of a `create`, `fetch`, `generate` or `get` method to be the first statement of the body, so it can block the very move that would buy that second blank line. The two can close off every arrangement at once, and then the inline form is not a compromise but the only legal shape. Outside that pattern both forms compile and format clean, and the choice is the author's.
- `OperatorOperandCheck` forces the extraction when a multiline call becomes an operand of a comparison, so that local stays even though it is used once.
- An extraction can force a rename. A second value of the same kind in one scope means neither can keep the plain name, and `MissingEmptyLineCheck` requires a blank line where a variable's reference chain ends, which can split an assertion block that would otherwise be contiguous. A numbered name such as `layout1` and `layout2` is for several values of the same kind that have no better name and that the code really needs, and a new one comes only after the code reuses an existing variable that plays the same role. So an extraction that needs a numbered name, an odd name, or a reassignment of the same local is not necessary. If no variable for the value exists in scope, keep the nested call inline.

**Rationale:** The measure is what the next reader has to hold in their head, not the line count. A name that restates the call it came from costs a line and buys nothing. An extraction that the code does not need also adds a name. Often that name is odd, or numbered, such as `layout1` and `layout2`, or the code must reassign the same local, as in `layout = update(layout, ...)`. A variable that already holds the value adds no new name, and passing it removes a call that the reader must check for the same result. Thus a nested call stays inline unless a variable for that value already exists in scope, or a new name says more than the expression does.

Rule 502 answers the same question for a `private static final` constant used once, and rule 203 decides where a local that survives is declared.

A violation is a single use local whose name only echoes the call that produced it, or a call passed inline as an argument while a variable in the same scope already holds its value. A nested call passed inline with no variable for its value in scope is not a violation, whatever its depth and whatever the argument count of the call it feeds.

**Example:** LPD-108819 Resolve a page's master page in its scope group (https://liferay.atlassian.net/browse/LPD-108819) kept `LayoutTestUtil.updateMasterLayoutPageTemplateEntryERC(LayoutTestUtil.addTypePortletLayout(stagingGroup), masterLayoutPageTemplateEntry.getExternalReferenceCode(), depotGroup.getExternalReferenceCode())` inline in `LayoutImplTest`. The review asked for `Layout layout = LayoutTestUtil.addTypePortletLayout(stagingGroup);` because the outer call takes three arguments. That local has the same name and type as the result of the outer call, so the code had to reassign it as `layout = LayoutTestUtil.updateMasterLayoutPageTemplateEntryERC(layout, ...)`, and `MissingEmptyLineCheck` added a blank line after the declaration. No variable held the value before, so the local reused nothing and only added a name. LPD-99541 Technical Task | Optimize Localization URL Strategy to Eliminate Redundant Indexing (https://liferay.atlassian.net/browse/LPD-99541) settled both directions in one file. `String canonicalURL = PortalUtil.getCanonicalURL(...)`, used once, was inlined, while two `_generateURL(...)` calls that wrapped across three lines inside `Assert.assertEquals` were extracted to `englishAlternateURL` and `spanishAlternateURL`, which in turn forced the plain `alternateURL` already in that scope to take its locale qualifier back. LPD-101584 settled the collision. `FragmentEntryLinkLocalServiceImpl.getGroupFragmentEntryUsageCounts` passes `_getFragmentEntryScopePredicate(_groupLocalService.getGroup(fragmentEntry.getGroupId()))` inline, two calls deep, and the reviewer asked for a `Group group` local on the strength of a call depth trigger that this rule no longer has, and of two sites in the same file that do extract one. Every arrangement fails: with the accumulator first, `VariableDeclarationAsUsedCheck` reports "No need to declare variable group"; moving `group` above it silences that and trips `ReturnVariableDeclarationAsUsedCheck` on `groupFragmentEntryUsageCounts` instead; moving the accumulator down to its first use trips both. The two cited precedents survive because they use `group` as a receiver, and the code the method was moved from survived because an unrelated declaration gave it a second blank line. Only renaming the local so the `(?i)_?get<VariableName>` regex misses it formats clean, and naming a variable to evade a check is not a fix.
