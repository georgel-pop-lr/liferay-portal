# 205: Order Declarations by the Call They Feed

When a block of local variables exists only to feed one call that follows it, order the block by that call's argument order and keep the declarations together, immediately above the call. A local the call does not take moves down to its own first use. Alphabetical order is the fallback, for a block that feeds nothing with an order of its own, and the tie breaker inside a block whose values do not all flow into one ordered call.

Two things do not take a local out of the block. A local the call shares with a later statement still belongs to the block of its first consumer, in that call's argument order, rather than being hoisted above the block because another call needs it too. And a blank line between the declarations does not split the block: the block is the run of declarations immediately above the call, blank lines included, so a local separated from its neighbors by a blank line is still ordered with them.

Two constraints override the argument order:

- A declaration that consumes an earlier local in the same block stays after it, whatever position its argument occupies.
- The source formatter wins on the blank lines. `MissingEmptyLineCheck` requires a blank line after a declaration whose initializer references an earlier local, so such a block cannot be contiguous; leave the spacing as `formatSource` produces it and correct only the order.

**Rationale:** A block whose order matches the call below it can be read left to right against that call, so two values of the same type cannot be silently swapped at the call site, and a new argument has one obvious place to be declared. Ordering the same block alphabetically instead breaks that correspondence for no gain, since the call already imposes an order. Counted on `modules` at `6f4316ff300e5`, over the 1285 blocks of two or more consecutive declarations whose names are exactly the arguments of the next call: of the 736 where argument order and alphabetical order differ, 679 follow the argument order against 47 alphabetical and 10 neither, so argument order is the convention by roughly 14 to 1. Contiguity is the weaker half of the rule: of the 669 blocks whose declarations do not reference one another, 381 are contiguous and 288 keep blank lines, while every one of the 616 blocks that do reference an earlier local is blank separated, which is `MissingEmptyLineCheck` showing up in the data rather than a choice.

This rule is the missing piece between three neighbors. Rule 201 sorts an already grouped block alphabetically and explicitly declines to require the grouping; rule 202 covers sibling fields, methods, and functions, not locals; rule 203 gives the declare-late half and the wrapper exception. Where rule 201's alphabetical sort disagrees with this rule, the call's argument order wins for the locals feeding that call.

A violation is a block of locals feeding one call left in an order that is neither the call's argument order nor, absent an imposed order, alphabetical; or a local declared at the top of a method when the first statement that uses it comes later. Blank lines inside an independent block are a 57 percent preference rather than a rule, so raise them only alongside a wrong order. A local declared first because a later call reuses it, in an order that is neither the argument order of its first consumer nor alphabetical, is a violation too.

Sharing does not loosen the order. Counted on `modules/apps` at `24e6a0c4eb7e9`, over the 130 test blocks of two or more `RandomTestUtil.random*()` declarations that feed the next call and where at least one of them is reused by a later statement: 109 are in an order that is both the argument order and alphabetical, 7 follow the argument order against alphabetical, 13 are alphabetical against the argument order, and 1 is in neither. So 129 of 130 keep a sortable order despite the reuse. Where the two orders disagree the split is 7 to 13, and the alphabetical 13 are mostly numbered sets (`key1`, `key2`, `title1`, `title2`) and calls with no positional meaning (`StringBundler.concat`, JSON builders), which is the fallback this rule already names.

**Example:** Brian Chan closed https://github.com/brianchandotcom/liferay-portal/pull/180260 with "ordering is very off" and hand fixed part of it (https://github.com/brianchandotcom/liferay-portal/pull/180260#issuecomment-5292474243). In `AUITopHeadCSSDynamicIncludeTest.testInclude` a `MockHttpServletRequest` and a `MockHttpServletResponse` opened the method as a pair; the request belonged with `auiTopHeadCSSDynamicInclude` and `href` in the argument order of the `ReflectionTestUtil.setFieldValue` call that used all three, and the response belonged just above the `include` call, its only user. The two `DynamicInclude` tests already in the codebase do exactly that, declaring the response immediately before `include` and building the request through a helper (`ClientExtensionTopHeadDynamicIncludeTest` line 131, `ConsentManagementPlatformTopHeadDynamicIncludeTest` line 63). The habit the pull followed instead is a minority: of the 71 files that declare both mocks, 15 declare them consecutively and 56 do not.

**Example:** Brian Chan's commit https://github.com/brianchandotcom/liferay-portal/commit/96cfec34eb7625f5f2b388b58860b5506346047d (`LPD-105565 SF`) fixed `LayoutsAdminDisplayContextTest._testGetVerticalNavItemListWithDepotGroup`. `String name` was declared first, followed by a blank line and then `long layoutPageTemplateCollectionId1`, because `name` also feeds the second `_getLayoutPageTemplateCollection(layoutPageTemplateCollectionId2, name)` call further down. He moved `name` under `layoutPageTemplateCollectionId1`, contiguous and in the argument order of `_getLayoutPageTemplateCollection(layoutPageTemplateCollectionId1, name)`, its first consumer, which matches the `designLibraryGroupId`, `title` pair feeding `_setUpDesignLibraryGroup` a few lines above. The liferay review had passed this block twice, since the reuse and the blank line together meant that it no longer read as one block feeding one call.
